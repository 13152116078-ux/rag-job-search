# RAG 知识库问答系统 · 完整实施方案

> 目标岗位：LLM 应用工程师 / 大模型应用开发实习
> 预计周期：14 天（每天 3-4 小时）
> 硬件要求：无 GPU 也能跑（嵌入和重排都可用 CPU 或 API）

---

## 一、项目定位

**一句话**：给一个垂直领域构建「能溯源、可评估、抗幻觉」的知识库问答系统。

**为什么选这个方向做**：
- 现在 LLM 应用岗 90% 的实际工作就是 RAG
- 它能把「检索」「重排」「生成」「评估」四件事完整串起来，每一环都有技术深度可讲
- 有明确的量化指标（召回率、faithfulness），简历上能写数字

**建议的数据源**（三选一，选你能收集到最多的）：
1. **AI 岗位 JD 库** —— 爬招聘网站 500-1000 条 AI 相关 JD，做成「岗位匹配问答」。你自己找工作也用得上，最真实
2. **开源框架文档** —— 比如 FastAPI / LangChain 官方文档，做成「文档助手」
3. **专业资料** —— 某门课的教材、论文摘要、行业报告

> 建议选 1，因为面试官问「为什么做这个」时，你能答「我自己在找工作，想解决信息过载」。

## 二、技术架构

```
文档(PDF/HTML/MD)
   ↓ 解析(pdfplumber / BeautifulSoup / markdown)
清洗(去页眉页脚、去重、normalize)
   ↓ 切片(固定长度 + 重叠，或按标题层级)
Chunk 集合
   ↓ 向量化(BGE-M3)
向量库(Chroma)
   ↓ ────────────────────────┐
用户问题                    │
   ↓                       │
Query 改写(可选)             │
   ↓                       │
混合检索 ◄──────────────────┘
   ├── 向量检索 (BGE-M3 + Chroma)
   └── 关键词检索 (BM25 / rank_bm25)
   ↓ 合并去重(RRF 融合)
候选 Top-20
   ↓ 重排(bge-reranker-v2-m3)
Top-5
   ↓
Prompt 组装(带引用编号)
   ↓
大模型生成(DeepSeek API / 本地 Qwen2.5-7B)
   ↓
输出答案 + 引用来源
```

## 三、分阶段实施

### 阶段 1：数据准备（2 天）

**任务**：
- 确定数据源，写爬虫或批量下载器
- 文档解析：PDF 用 `pdfplumber`，HTML 用 `BeautifulSoup`，先用 `trafilatura` 抽正文更干净
- 清洗：去掉导航栏、页脚、重复段落
- **切片**：`chunk_size=512`，`overlap=64`（中文按字符数算更准）
  - 进阶：按文档标题层级切，避免把一个概念切碎

**产出**：`chunks.jsonl`，每行 `{id, source, title, text, meta}`

**这一步的坑**：
- 中文 PDF 常出现换行断裂 → 用 `pdfplumber` 的 `extract_text(layout=True)` 或先做断行合并
- 表格内容会被切碎 → 表格单独抽出来存成结构化文本

---

### 阶段 2：基础 RAG 打通（3 天）

**任务**：
- 接入 `BGE-M3`（`sentence-transformers` 加载，本地 CPU 可跑，首次下载约 2GB）
- 建立 Chroma 集合，批量写入向量
- 写检索函数：`query → top_k 向量检索 → 拼 prompt → 调 LLM`
- 先跑通「一个问题 → 一个答案」的闭环

**这一版的目标是能跑，不是好**。跑通之后再做优化。

**Prompt 模板**（关键）：
```
你是一个严谨的问答助手。请仅根据下面提供的资料回答问题。

资料：
[1] {chunk_1}
[2] {chunk_2}
...

问题：{question}

要求：
1. 只使用资料中的信息作答，资料没有的内容直接说「资料中未提及」
2. 每句话结尾标注引用的资料编号，如 [1]
3. 不要编造
```

---

### 阶段 3：混合检索 + 重排（2 天）—— 这是拉开差距的地方

**为什么做**：纯向量检索对「专有名词、数字、代码」不敏感，BM25 能补上。

**实现**：
- `rank_bm25` 建关键词索引
- 两路各取 Top-20
- **RRF 融合**：`score = Σ 1/(k + rank)`，k 取 60
- 融合后取 Top-20 → `bge-reranker-v2-m3` 重排 → Top-5

**这一步做完，召回率通常能从 ~65% 提到 ~85%**。这个提升就是简历上的数字。

---

### 阶段 4：评估体系（2 天）—— 大部分应届生不做这个

**为什么做**：这是你和「只会调 API 的人」的分水岭。

**做法**：
1. **构造评测集**：人工标 100-200 条「问题 + 标准答案 + 应召回的 chunk id」
2. **检索评估**：算 `Recall@5`、`MRR`、`NDCG`
3. **生成评估**：用 RAGAS 算
   - `faithfulness`：答案是否忠于资料
   - `answer_relevancy`：答案是否切题
   - `context_precision`：召回的上下文有多少是有用的
4. **回归测试**：每次改代码就跑一遍，防止回退

**产出**：一张对比表

| 方案 | Recall@5 | Faithfulness | 平均延迟 |
|---|---|---|---|
| 纯向量 | 0.68 | 0.71 | 1.2s |
| +BM25 混合 | 0.82 | 0.79 | 1.5s |
| +重排 | 0.89 | 0.86 | 2.1s |

**这张表就是简历的核心竞争力。**

---

### 阶段 5：工程化（3 天，可选但推荐）

- 用 FastAPI 包一层 `/chat` 接口，支持流式输出
- 简单前端（Streamlit 最快，半天搞定）
- 记录每次调用的 token、延迟、成本
- 加一个「无答案」检测：相似度低于阈值就回「资料中没有相关内容」，**这条能显著降幻觉**

## 四、面试会被追问的点（提前准备）

**Q：切片长度为什么选 512？**
> 试过 256/512/1024。256 太碎，单个 chunk 信息不全，模型容易答一半；1024 召回精度下降，噪声多；512 在中文场景召回率和完整性的平衡最好。我用评测集验证过。

**Q：混合检索的权重怎么定？**
> 用的是 RRF 而不是加权求和，因为向量相似度和 BM25 分数不在一个量纲上，RRF 只看排名不看分值，更稳。k 值 60 是论文默认，我试过 30/60/100，差异不明显。

**Q：怎么控制幻觉？**
> 三层：① prompt 里明确要求「资料没有就说没有」；② 加相似度阈值，低于阈值直接拒答；③ 输出强制带引用编号，用户可以点进去核对。评估集里 faithfulness 从 0.71 提到 0.86。

**Q：多跳问题怎么处理？**
> 目前是单跳。改进方向是 query 分解——先让模型把复杂问题拆成子问题，逐个检索再合并。这是我下一步要做的。

**Q：为什么不用 LangChain？**
> 试过，但它的黑盒抽象反而让我不好控制检索和 prompt 的细节。RAG 的核心就在于这些细节，所以我手写了 pipeline，只有 200 行左右，反而更可控。
